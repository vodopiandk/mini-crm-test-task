# DECISIONS.md

По каждой развилке — что выбрали и почему (одна-две строки).

## Шаг 1: БД и API

- **Миграции** — один файл `migrate.sql` с `CREATE TABLE IF NOT EXISTS`,
  выполняется при каждом старте. Без фреймворка миграций: схема фиксирована
  ТЗ, версионность избыточна для 3-дневного MVP.
- **Сессия** — `cookie-session` (данные в подписанной cookie, без
  серверного хранилища), не `express-session`. Один общий пароль на всех —
  server-side store не нужен; плюс сессия не теряется при рестарте
  процесса, в отличие от `MemoryStore`.
- **Проверка пароля** — прямое сравнение с `ADMIN_PASSWORD` через
  `crypto.timingSafeEqual`, без bcrypt. Хранимого пользователя/хэша нет —
  пароль единственный общий секрет из `.env`, хэшировать нечего;
  `timingSafeEqual` закрывает тайминг-атаку без доп. зависимостей.
- **Валидация** — вручную (без zod/joi). Набор полей маленький и
  стабильный, отдельная библиотека — лишняя зависимость.
- **Экранирование вывода** — отложено на фронтенд (шаг 2), не на API.
  API отдаёт JSON, а не HTML; XSS-риск возникает в момент вставки в DOM —
  там и закрывать (textContent/ручной escape), а не задвоенно на бэке.
- **id сущностей** — `INTEGER PRIMARY KEY AUTOINCREMENT`, не UUID. Нет
  требования к непредсказуемым/внешним id, автоинкремент проще для MVP.

## Шаг 2: веб-интерфейс

- **Гейтинг доступа — на клиенте, не на сервере.** `express.static` отдаёт
  `index.html`/`login.html` всем без проверки; сам HTML не содержит данных,
  только JS-шелл. `app.js` при загрузке дёргает `/api/session` и уводит на
  `/login.html`, если не авторизован — а реальные данные лида всё равно
  закрыты `requireAuth` на уровне API. Проще, чем серверный роутинг двух
  статических страниц, требование «открытой ссылкой не утечёт» всё равно
  выполняется.
- **Экранирование — через `textContent`, без ручной escape-функции.** Весь
  вывод данных лида/тегов/сообщений строится через `document.createElement`
  + `textContent`, нигде не используется `innerHTML` с данными от
  пользователя. Проверено вручную XSS-пейлоадом
  (`<script>alert(1)</script>` в поле «Запрос») — рендерится как текст,
  не выполняется.
- **Модалки — нативный `<dialog>`, без библиотеки.** Два диалога
  (карточка лида, добавление лида), закрытие по Escape/клику на backdrop
  работает из коробки браузера.
- **Смена статуса — только в карточке**, не инлайн в таблице списка. Так
  явно сформулировано в ТЗ («Карточка лида: смена статуса...»); отдельный
  контрол в таблице был бы дублирующей логикой.
- **Создание тега — только из карточки лида** (поле «Новый тег» сразу
  создаёт и назначает), отдельного экрана управления тегами нет — ТЗ не
  требует, а список тегов для фильтра получаем тем же GET /api/tags.
- **Дубликат имени тега — обычный `alert()`**, без кастомного тоста/модалки.
  Это редкий edge-case (409 от API), дополнительный UI-компонент под него
  избыточен для MVP.
- **Авто-обновление — полный перерендер таблицы раз в 7 секунд** без
  диффа/сравнения с предыдущим состоянием. Список лидов для тестового
  задания небольшой, полный перерендер проще и не создаёт расхождений.
